## Confirmed issues to address

The current implementation has the following problems:

1. The client contains a hard-coded provider map while the backend already exposes `Providers`. The frontend never calls that service, allowing the two catalogs to drift.
2. Default model IDs are hard-coded and stale.
3. Model selection is a free-text input. Users must already know the exact model ID.
4. No capability information is shown, so users can select a text-only model while expecting image, audio, video, or file support.
5. No model pricing or request cost estimate is shown.
6. Runtime token usage is recorded, but monetary cost is not calculated or displayed.
7. Changing providers clears some fields but can retain credentials or authentication data from another provider.
8. The streaming checkbox is saved, but provider requests always force non-streaming mode.
9. Ollama’s CLI command is presented as a runtime option, but provider execution always uses HTTP. Do not introduce unsafe shell execution merely to make this field functional.
10. `RunAgent`, `InteractWithAgent`, and `TestAgent` accept only string messages. Provider payloads and conversation history are text-only.
11. The test console cannot attach or preview media/files.
12. Generated JSON/YAML can expose a raw API key. Secrets must be masked by default.
13. The “Other API” option claims a configurable custom schema, but its request and reply parsing are mostly fixed.
14. Model-specific parameter limits are not enforced. For example, output-token and temperature controls do not react to model capabilities.
15. Form loading assumes every saved configuration has all current nested fields and can fail on older configurations.
16. Agent and session JSON writes are not sufficiently protected against concurrent write corruption.
17. Anonymous identity/session behavior is derived from message content, preventing reliable conversation continuity while also making identity semantics unclear.

Fix these issues while preserving compatibility.
